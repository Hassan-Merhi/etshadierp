# ERP POS System

## Overview

This project is a comprehensive ERP and POS system designed for multi-company warehouse management. It focuses on optimizing operations and providing strong financial oversight for businesses dealing with bulk inventory and complex supply chains, including international container shipments. Key capabilities include robust inventory tracking across multiple locations, streamlined purchase order management, container tracking, and full financial accounting and reporting. The system supports multi-entity businesses with isolated data and features an AI Chatbot for intelligent assistance with ERP data.

## User Preferences

Preferred communication style: Simple, everyday language.

## System Architecture

### UI/UX Decisions

The frontend uses React with TypeScript and Vite, employing the `shadcn/ui` design system (New York style) built on Radix UI primitives and styled with Tailwind CSS. It prioritizes clarity and efficiency for data-intensive interfaces, using Inter and JetBrains Mono fonts, and supports light/dark themes. A consistent vertical sidebar navigation pattern is used across all major pages, featuring `w-56` width, uppercase group labels, active state styling, and icons from `lucide-react`.

### Technical Implementations

The system is a full-stack TypeScript application. The frontend utilizes React, Vite, TanStack Query for server state, `react-hook-form` with Zod for forms, and `wouter` for routing. The backend is an Express.js server providing a RESTful API, with Zod used for shared validation. Data is stored in PostgreSQL, accessed via the native `pg` driver and Drizzle ORM for type-safe queries and schema management, supporting multi-currency and Drizzle Kit for migrations.

Key features include:
-   **Security Hardening — Customer-Order Bale Pick Race Fix (May 2026, Batch G2)**: Extended the Batch G fix to four bale-pick sites in `server/routes/factory/factoryCustomerOrderRoutes.ts` that had the same SELECT-then-UPDATE pattern. Three of the four (single bale scan-add `~L500`, bulk-import refnum `~L734`, bulk-import article `~L840`) were not even wrapped in a transaction — the bale lookup ran on `db`, then `INSERT customer_order_bales` and `UPDATE factoryBales` ran on `db` separately, so two concurrent imports for the same article could insert duplicate join-rows pointing to the same physical bale. Fix: each handler now does its critical section inside `db.transaction(async tx => …)` with `.for("update")` on every bale SELECT. Single-add wraps the whole pick + alreadyAdded check + V5 cross-order dup check + proforma overload + insert + status flip in one tx, and uses a typed `PickResult` sum returned from the tx to map business-rule failures back to the original HTTP status codes (404 for missing bale, 400 with `overloaded`/`notInProforma` flags). Bulk-import REFNUM uses one tx per refNum (avoids holding locks across a 500-row import), with the V5 cross-order check inside the tx. Bulk-import ARTICLE uses one tx per article that locks `qty*5` candidate bales, then per-candidate re-runs the V5 cross-order dup check inside the tx (architect-flagged: the outer `v5BlockedBaleIds` snapshot can be stale by the time we hold the locks — re-checking inside the tx closes that V5 window because V5 bales stay IN_STOCK and the lock alone doesn't block a concurrent picker). Exchange handler (already in tx) just gained `.for("update")` on the new-bale SELECT. Bale-status updates by known id (delete bale from order, finalize, unfinalize, cancel, restore-loading) were intentionally left alone since they don't have a pick race. Architect review returned PASS.
-   **Security Hardening — Concurrency / Bale Pick Race Fix (May 2026, Batch G)**: Four factory POS bale-pick sites in `server/routes/factory/factoryEmployeesPosRoutes.ts` were doing `SELECT … WHERE status='IN_STOCK' ORDER BY id LIMIT qty` followed by `UPDATE … SET status='SOLD'` without a row lock. Two concurrent sales for the same product/location could pick the same physical bales — both transactions would commit and one bale would be marked SOLD twice in the audit trail with the second sale's customer effectively getting "phantom" inventory. Added Drizzle `.for("update")` to all four sites: POS sale POST (line ~1636, IN_STOCK→SOLD), POS sale PUT restore (line ~1834, SOLD→IN_STOCK to roll back the previous sale items), POS sale PUT re-pick (line ~1894, IN_STOCK→SOLD for new items), and POS sale DELETE/void (line ~2081, SOLD→IN_STOCK to release). Under PostgreSQL READ COMMITTED, a second transaction blocks on the locked rows, then re-evaluates the WHERE clause after the first commits and correctly skips rows whose status is no longer IN_STOCK (or no longer SOLD for the reverse direction). In addition to the lock, both IN_STOCK→SOLD picks now enforce `availableBales.length === requestedQty` and throw `INSUFFICIENT_BALE_STOCK` to abort the whole transaction if fewer physical bales exist than the customer is being billed for — preventing a "phantom inventory" sale from going through under low-stock or lock-contention conditions. The two reverse direction picks (SOLD→IN_STOCK on edit-replace and on void/delete) intentionally do *not* enforce strict count, because legacy sales may legitimately have fewer SOLD bale rows than their line quantity (early data, manual cleanup, etc.) and blocking edits/voids of those would be a regression. Customer-order bale picks (`factoryCustomerOrderRoutes.ts` single-add, bulk-import, exchange) have the same pattern but several of those paths are not even wrapped in a transaction — flagged as Batch G2 follow-up. The architect-suggested CTE-based single-statement pick (`WITH picked AS (… FOR UPDATE LIMIT n) UPDATE … FROM picked RETURNING id`) was considered but deferred since the current two-step approach is now correct under READ COMMITTED.
-   **Security Hardening — Sales Voucher Delete Inventory Desync Fix (May 2026, Batch E)**: `storage.deleteVoucher()` (server/storage.ts:3403) for Sales vouchers no longer does inline inventory math. The previous code did a raw `tx.update(inventory)` with a simple weighted-average computation that (1) skipped negative-layer settlement and (2) used a different cost formula than the canonical `adjustInventory()` helper, producing inventory desync whenever a Sales voucher was deleted on stock that had previously gone negative. The Sales branch now calls `adjustInventory(tx, locationId, stockItemId, +qty, companyId, costPrice, "Sales-Reversal", voucherId)` per line item, which routes through the same `SELECT … FOR UPDATE` + negative-layer settlement path used by all other inventory mutations (POS sale, POS edit, Sales voucher edit with location change). Currently the only caller is `fiscalTransferRoutes.ts` rolling back a fiscal transfer dispatch, but the bug also affects any future caller. The Stock Transfer / Production / Consumption / Mixed / Stock Adjustment branches in the same function still use the old inline pattern — flagged for a follow-up batch but out of scope for the POS desync fix.
-   **Security Hardening — Transactional Safety + WhatsApp Tenant Isolation (May 2026, Batch B+D)**: (B) `whatsapp_recipients` is now per-tenant. Schema migration in `server/index.ts` added `company_id integer` column, dropped the old global `whatsapp_recipients_chat_id_key` UNIQUE constraint, and created a new `whatsapp_recipients_company_chat_unique` UNIQUE INDEX on `(company_id, chat_id)` so the same WhatsApp group can be configured by multiple tenants without conflict. All four user-facing recipient CRUD endpoints (`GET/POST/PUT/DELETE /api/whatsapp/recipients`) and both user-facing send-path lookups (`/api/whatsapp/send-np-all-now`, `/api/whatsapp/send-stock-report`) in `server/routes/whatsappRoutes.ts` now scope strictly to `req.session.currentCompanyId`. Previously a tenant could list, edit, delete, or send through any other tenant's WhatsApp group. Server-driven schedulers (`schedulerService.ts`) intentionally not changed since they look up recipients by id from per-company `whatsapp_stock_settings` / `net_position_export_settings` rows, not from session. ## Offline-First Architecture (Mar 2026)

The app has a layered offline-first foundation:

### IndexedDB Layer (`client/src/lib/db.ts`) — Schema v3
- Uses **Dexie.js** (v4) for typed IndexedDB access
- Schema tables: `syncQueue`, `syncState`, `syncLogs`, `conflicts`, `localDrafts`, `offlinePackages`, and entity cache tables
- `syncQueue` v2+ fields: `idempotencyKey`, `mode`, `entityType`, `operation`, `payload`, `url`, `method`, `companyId`, `locationId`, `status`, `retryCount`, `nextRetryAt`, `lastError`, `description`
- `conflicts` v3+ fields: `syncQueueItemId`, `entityType`, `operation`, `localPayload`, `serverResponse`, `conflictReason`, `url`, `method`, `resolved`, `resolvedAt`, `resolution`
- `syncLogs` pruned to 500 entries; `appendSyncLog()` always best-effort
- Helpers: `addToSyncQueue()`, `getSyncQueueCount()`, `getConflictCount()`, `getUnresolvedConflicts()`, `resolveConflict()`, `addConflict()`, `getGlobalSyncState()`, `upsertGlobalSyncState()`, `clearAllOfflineData()`

### Sync Engine (`client/src/lib/syncEngine.ts`) — Part 3 upgraded
- `runSync()` is idempotent and serialized (no concurrent runs)
- **Exponential backoff**: skip items where `nextRetryAt > now`; backoff = min(3s × 2^retryCount, 120s)
- **Error classification**: 401 → auth redirect; 409 → conflict; 4xx → permanent fail (no retry); 5xx/network → retry with backoff
- **Max retries**: items with `retryCount >= 5` are permanently marked failed
- **Conflict detection**: 409 responses → write to `conflicts` table (with url/method for retry), remove from queue
- **Queue deduplication** via `deduplicateQueue()`: multiple PATCH/PUT to same URL → collapse to latest payload
- Emits `erp:sync` events with `conflictDetected` flag
- Auth redirect on 401 during sync

### ConnectivityContext (`client/src/contexts/ConnectivityContext.tsx`) — Part 3 upgraded
- Global `ConnectivityProvider` wraps entire app
- Exposes: `isOnline`, `isSyncing`, `status`, `lastSyncedAt`, `pendingCount`, `failedCount`, **`conflictCount`**, `triggerSync()`, `refreshCounts()`
- `conflictCount` = number of unresolved conflicts in IndexedDB
- Pings `/api/health` on online/offline events AND every 30 seconds
- Refreshes counts (including conflicts) every 15 seconds

### Offline Queue (`client/src/lib/offlineQueue.ts`) — Part 3 deduplication
- SAFE_PATTERNS covers: POS, all ERP vouchers, all factory endpoints, stock adjustments/transfers, bale transfers
- **Deduplication**: PATCH/PUT to same URL → replaces existing pending item's payload (no duplicate edits queued)
- **DELETE dedup**: removes preceding POST/PATCH for same URL

### Conflict Center — New in Part 3
- **`client/src/pages/ConflictCenter.tsx`**: Review page at `/conflicts` and `/factory/conflicts`
  - Lists all unresolved sync conflicts
  - Shows entity type, timestamp, conflict reason
  - "Accept server version" → marks resolved, discards local
  - "Retry local version" → re-queues local payload to IDB sync queue, marks resolved
  - "Dismiss all" button to batch-clear
  - Expandable diff view: local JSON vs server response side by side
- **Conflict badge in AppSidebar** and **FactorySidebar**: orange "Conflicts (N)" entry appears when `conflictCount > 0`

## Security & Data-Integrity Audit (May 2026)

A 52-finding audit was applied across batches A–G, G2, F. Code-level fixes (batches A–G, G2) are committed and ship via the normal deploy. Schema/index changes follow a different path described below.

- **Batches A–E, G, G2** — input validation, authZ, CSRF, file-upload safety, rate-limiting, secret hygiene, error redaction, etc. (committed).
- **Batch F-Phase 1 (May 2026) — Composite indexes on tenant scoping**:
  - 59 `companyIdx: index("<table>_company_idx").on(t.companyId)` entries added to `shared/schema.ts` covering every multi-tenant table missing one.
  - All 59 `CREATE INDEX IF NOT EXISTS` DDLs applied to dev DB in a single transaction.
  - The same 59 DDLs are also wired into the runtime startup `migrations` array in `server/index.ts` (just before the array close, marked with a `F-Phase 1 (May 2026)` comment) so they run automatically on every fresh boot — including production — using the same idempotent path the rest of the schema uses.
  - Substantial improvement to per-tenant query performance with zero behavioural change.
- **Batch F-Phase 2 (FK constraints) — DEFERRED**:
  - 12 clean FK constraints (e.g. `voucher_entries.voucher_id → vouchers.id`, `customer_orders.customer_id → customers.id`, etc.) were prepared with orphan checks (all clean) and per-FK `ON DELETE` semantics chosen.
  - Blocked by a pre-existing dev-DB drift issue: most tenant parent tables (`vouchers`, `customers`, `companies`, `customer_orders`, `factory_bales`, `purchase_orders`, `container_offloads`, `stock_items`, `factory_bale_products`) currently have **no PRIMARY KEY constraint** in dev (only auto-generated NOT-NULL CHECKs and a `*_id_seq` sequence on the id column). PostgreSQL refuses `ADD CONSTRAINT FOREIGN KEY` against an unconstrained column.
  - Schema.ts was reverted for these 12 FKs to avoid breaking deployment if production exhibits the same PK gap.
  - Resolution path (separate future batch, requires user approval): audit prod DB PK presence; if missing, apply `ALTER TABLE … ADD PRIMARY KEY (id)` after verifying id uniqueness; then re-apply Phase 2 FK additions to both schema.ts and DBs.
- **Batch F-Phase 3 (long-tail FKs)** — deferred (also blocked by missing PKs).
- **Pre-existing migration approach**: the dev DB is bootstrapped via raw `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD COLUMN IF NOT EXISTS` SQL embedded in `server/index.ts` (the `migrations` array), NOT via `drizzle-kit push`. `drizzle-kit push` is currently blocked by drift (e.g. `fiscal_period_closures` has fewer columns in dev than in schema). Schema.ts edits are still authoritative for any future clean rebuild but are NOT auto-applied at runtime.
- **Batch H (May 2026) — Cleanup nits**:
  - **SQL injection hardening** — replaced ~14 `sql.raw(...)` interpolation sites with parameterised binding: `adminRoutes.ts` orphaned-voucher delete (6 statements, now `= ANY(${ids})`) and the bulk-clear flow (now `inArray(...)`); `factoryEmployeesPosRoutes.ts` employee-advances and repayments GET, plus `employee-bonuses` and `worker-bonuses` GET (now built with nested `sql\`...\`` fragments instead of string concatenation); `factoryProductionPlannerRoutes.ts` 3 `ARRAY[${ids.join(',')}]` sites (now `ANY(${ids})` direct array binding). **One real SQL injection vector closed**: `GET /api/factory/worker-bonuses?status=…` previously interpolated `req.query.status` directly into the SQL string (`AND wb.status = '${status}'`). Most other touched sites had numeric inputs or DB-sourced data so were safe in practice, but the pattern was fragile against future edits. ~30 similar `sql.raw(\`ARRAY[${ids.join(',')}]\`)` sites remain in factory allocation/supplier/customer-proforma routes; all use numeric IDs or properly-escaped string codes and are out of scope for this batch (candidate for Batch I).
  - **Empty catch fixed** — `authRoutes.ts:438` `} catch (_) {}` now logs via `console.warn`.
  - **Unwrapped `JSON.parse` calls wrapped** — 3 sites in `factoryProductionPlannerRoutes.ts` (×2) and `factoryDocsUsersRoutes.ts` now fall back gracefully on bad JSON instead of throwing an uncaught 500.
  - **Helmet middleware added** — `server/index.ts` now installs `helmet` with safe defaults (`X-Frame-Options DENY`, `X-Content-Type-Options nosniff`, HSTS, `Referrer-Policy`). `contentSecurityPolicy` and `crossOriginEmbedderPolicy` are intentionally disabled to avoid breaking the Vite-served SPA and external image loads. Package: `helmet ^8.1.0`.
  - **Auth + path-traversal fixed on 3 file-serving routes**: `/api/pos/temp-pdf/:id` (added `requireAuth`), `/api/factory/uploads/bale-photos/:filename` and `/api/factory/uploads/workers/:filename` (added `requireAuth` plus `path.basename` + `path.resolve` containment check so `../` traversal is rejected with 400).
  - **Verified clean** (no action): cookie/session security flags, trust proxy, body-parser limits, hardcoded secrets, `eval`/`Function`, `dangerouslySetInnerHTML` (all 7 sites are static print CSS), TODO/FIXME (only XXX placeholders in regex/comments), and the remaining 9 unauth'd routes (login, logout, presence-leave, 5 CSV templates, dev-only seed gated by `NODE_ENV`).
  - **Deferred**: full CSRF middleware (cookie `SameSite=lax` already mitigates the common cases), and reducing the 170 `console.log` calls in server code (operational noise, not a security issue).
